# 项目定位卡

先判断项目处于什么状态，再用四个独立维度描述它。四项只用于分别决策，**不要相加成项目等级**。

## 项目状态

| 状态 | 判据 | 最低要求 | 暂不要求 |
| --- | --- | --- | --- |
| scaffold | 只有想法、模板或空仓库 | 目标、数据边界、下一次验证 | 数据库、队列、CI、发布流程 |
| prototype | 正在验证核心行为，数据可丢弃 | 可运行入口、临时数据、失败可重来 | 兼容层、复杂部署、长期迁移 |
| active | 已有真实使用或持续维护 | 定位卡、Git、备份、基础验证、恢复路径 | 无触发条件的重型组件 |
| frozen | 暂停演进，但仍需可运行 | 运行说明、备份、恢复路径 | 新功能、迁移、依赖升级 |

项目从 prototype 进入 active 的条件是出现真实使用、需要保留的数据或持续交付责任；不要只因为代码变多就升级。

## 四维判据

### 责任面

看失败后果，不只看用户数量。

- R0 可丢弃：失败只损失一次运行或临时输出，没有依赖者。
- R1 个人/可恢复：只有自己或小范围使用；失败麻烦，但能重做或从备份恢复。
- R2 对外/不可逆：有外部用户、公开内容、不可重建数据、声誉或资金后果；必须有恢复路径。

判断问题：谁依赖结果；失败是否对外可见；数据或状态能否重建；恢复需要多久。

### 运行面

看部署单元和状态边界。

- S0 单次/本地：运行后退出，没有常驻服务。
- S1 单机常驻：桌面应用、本地服务或 NAS 单机服务；一个主进程或少量固定进程。
- S2 多实例/多服务：多个主机或进程独立运行、扩展或故障隔离。

判断问题：需要 24 小时在线吗；有几个部署单元；是否需要独立 worker；失败是否必须隔离。

### 数据面

看恢复要求和并发形状。

- D0 可重建：缓存、派生文件、可重新抓取的数据。
- D1 需备份：用户文件、历史记录、索引；单写者为主，需要备份和迁移保护。
- D2 强一致/多写：多写者、跨实体事务、审计或强约束；需要数据库事务和更严格的恢复流程。

判断问题：数据丢了能否重建；是否需要事务；有几个写者；是否跨进程或跨机访问；迁移失败能否回退。

### 协作面

看维护者数量，不看用户数量。

- C0 个人：一个主要维护者，分支和 CI 以降低个人负担为主。
- C1 小团队：多人修改、需要权限和审查边界。
- C2 公开协作：外部贡献者、公开 issue/PR、需要更明确的治理和兼容策略。

## 组合示例

| 组合 | 含义 | 典型处方 |
| --- | --- | --- |
| R2 + S1 + D1 + C0 | 高责任、单机、数据需备份、个人维护 | 保留简单运行时，重点做备份、发布、恢复和真实验收 |
| R2 + S1 + D2 + C0 | 高责任、单机、多写关系数据、个人维护 | 可以使用 Postgres、worker 和队列，但每个组件要对应真实业务 |
| R1 + S1 + D1 + C0 | 个人工具、单机、可恢复数据 | 一个仓库、一个进程、SQLite 或本地文件即可 |
| R0 + S0 + D0 + C0 | 一次性实验 | 只保留运行入口和数据边界，不建长期设施 |

定位卡不是一次性文档。项目进入 active、增加真实用户、改变数据恢复要求或准备发布时，重新填一次。
