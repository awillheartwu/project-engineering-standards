# 组合校准案例

这些案例用于校准判定，不是必须复制的模板。项目变化后要重新核对配置、数据和真实使用情况。

| 项目 | 四维画像 | 当前结论 | 关键证据 |
| --- | --- | --- | --- |
| **reYunPlex** | R2 / S1 / D1 / C0 | 高责任 + 低基础设施，保留 | 外部使用、单机 NAS、SQLite/本地数据；发布和恢复比数据库品牌更重要 |
| **AVNDB** | R2 / S1 / D2 / C0 | 高责任 + 高基础设施，有业务证据 | 39 个数据模型、多用户投稿/审核、版本与审计、外部同步、AI 长任务；Postgres/Redis/BullMQ/worker 对应真实边界 |
| **gsg** | R1 / S1 / D1 / C0（按当前配置） | 低实际使用 + 高基础设施，架构大于场景 | 注册关闭、单一 GitHub 用户；却有双仓库、Postgres/Redis、三组队列和 Bull Board。若转为多用户产品，重新评估 |
| **lirating** | R2 / S1 / D1 / C0 | 高责任 + 低基础设施，保留 | 真实 QQ 群和插件分发；SQLite + 文件足够；重量在发布、重载、回滚和真实群验收 |
| **DiscordManager** | R2 / S1 / D1 / C0 | 高责任 + 低基础设施，保留 | Discord 社区、24 小时 Bot；一个仓库/容器、JSON 状态、日志、锁和恢复；没有 Postgres/Redis/队列 |
| **SceneVault** | R2 / S1 / D1 / C0 | 高数据责任 + 低服务器基础设施，保留 | Windows 本地优先桌面应用；Tauri/Rust/Vue + SQLite + 可选 Python sidecar；重点在文件生命周期、备份恢复和 Windows 实机验收 |

## 从案例得到的稳定结论

- 外部用户、常驻运行和数据重要，不自动推出 Postgres、Redis 或队列。
- 高基础设施只有在数据形状、并发、长任务或故障隔离出现真实需求时才成立。
- 低责任项目也可能有高基础设施；这是错配信号，应优先收敛而不是继续加码。
- 桌面、插件、静态页面和单机服务可以采用完全不同的交付形态，但共享同一套责任与数据判据。
- 项目仍是脚手架或已经冷冻时，不进入完整规范；先确认是否值得继续。

## 使用边界

这些案例全部是个人维护、单机/NAS/桌面场景，不能证明多人团队、强合规或多租户场景。出现新的协作或合规压力时，补充真实案例后再扩展规范。
