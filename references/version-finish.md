# 版本收尾与交付检查

版本收尾是 active 项目从日常开发进入可交付状态的检查点。只有用户明确要求当前版本进入版本收尾，才启动测试、清理和交付准备；讨论、计划或提到“收尾”都不算启动授权。

build 和 CI 不是普适步骤：有交付物才构建/打包；有共享或部署代码才需要 CI。没有 build 就记录“无构建产物”，没有 CI 就记录本地检查和人工验收，不假装存在这一层。清理则适用于所有项目。

## 0. 确认交付类型

| 类型 | 主要产物 | 真实验收对象 |
| --- | --- | --- |
| 服务器/常驻服务 | 镜像或可运行包、部署配置 | 目标环境中的运行版本、健康检查、关键行为、回滚 |
| Windows/macOS 桌面应用 | 安装包、升级包 | 目标操作系统上的安装、升级、启动、数据恢复 |
| 平台插件 | 插件包或 Git 归档 | 干净实例安装、配置、真实平台行为、重载 |
| 静态页面 | 构建目录或静态包 | 实际访问、缓存、版本和资源完整性 |
| 本地工具/脚本 | 可执行文件或源码入口 | 一条命令运行、样本数据、失败路径 |

交付类型在定位卡里已经确定。版本收尾时只确认，不在此时扩大范围。

## 1. 冻结范围

- 记录目标版本、分支、需求范围、已知缺陷和明确延期项。
- 保留工作区中与本次版本无关的修改；只暂存本次范围。
- 检查远端分叉；有他人提交时先合并审阅，不强推覆盖。
- 冻结后新增需求默认进入下一版本，除非用户明确改变范围。

## 2. 数据与配置

- 列出本次涉及的数据库迁移、配置变更、文件格式变化和用户数据处理。
- 数据面 D1/D2 在迁移前生成备份，并验证备份可读取、可恢复。
- 预览迁移影响；准备回退路径。失败时保留现场，不自动回滚数据库。
- 真实配置和密钥留在仓库外；测试使用临时数据，不连接生产环境。
- 没有数据变更时，也要在报告中明确写“无数据变更”，不要省略。

## 3. 清理

清理是独立阶段，先于构建和人工验收。它不需要 build 或 CI，但必须有引用证据。

- 过时文档：按 references/documentation.md 合并、删除或归档；保留仍在使用的运维、ADR、发布说明。
- 过时测试：按 references/testing.md 删除失效、重复和锁实现细节的测试。
- 空文件、空文件夹：删除；只有运行时或版本控制必须存在时才保留占位。
- 空函数、空导出：确认没有调用方后删除；公共 API 占位必须明确报错，不能静默成功。
- 孤儿代码、资源、配置和依赖：检查 import、路由、CLI、插件入口、动态加载、配置和脚本引用；不要只按文件名猜。
- 临时产物：coverage、dist、缓存、截图、测试数据和日志，按策略清理或保留。
- 清理与功能改动分开提交；批量删除前确认引用图和动态入口。
- 无法确认是否仍被动态加载的对象，先记录并保留，不要为了“干净”冒险删除。

清理不要求把所有历史都删掉；CHANGELOG、release notes、仍有效的 ADR、数据恢复说明和必要的兼容层应保留。清理完成或明确记录延期，再进入验收。

## 4. 测试与证据

- 按 references/testing.md 盘点、删除和补充测试；测试是风险证据，不是覆盖率指标。
- 校验行为契约、权限边界、数据保护、失败恢复和本次已确认缺陷。
- 有性能预算的项目，按 references/performance-and-ci.md 检查启动、内存、延迟、吞吐、队列积压或包体积；没有预算就记录缺口，不临时造大规模压测。
- 测试数据必须可丢弃；真实用户数据、真实群消息和生产数据库不能作为自动测试夹具。
- 记录运行过、跳过和无法运行的检查及原因。

## 5. 检查与交付物准备

- 使用项目约定的本地检查；有 CI 时确认 CI 覆盖同一范围，没有 CI 时明确记录本地检查边界。
- 只在交付类型需要时 build/package/archive；没有构建产物就写“无构建产物，使用源码/运行入口”。
- 在干净环境从确定提交准备交付物；记录版本、提交 SHA、镜像 digest 或安装包校验值。
- 有性能或包体积预算时，记录实际值；没有预算时记录基线或未测原因。
- 中途改代码后，只重跑受影响项；不要重复无效的整套检查。
- 部署和分发复用已验收产物，不在部署阶段重新构建另一个版本。

## 6. 人工验收

- 人工验收是发布、分发以及 main 自动部署项目合并前的必要闸门；AI 不能代替用户做最终验收。
- 验收必须绑定确定的候选提交和产物，写清环境、版本/SHA、操作路径和结果。
- 至少覆盖本版关键用户路径、明显失败路径、数据迁移/恢复和安装/升级边界。
- 验收失败时回到 dev 修复并重新验收；不能把“修完应该没问题”当作通过。
- 如果合并到 main 会产生新提交而不是快进，原验收失效，需要按新提交重新验收。
- 验收证据要保留在交付报告中；不能只写“已人工验收”。

## 7. 合入 main

- 合入 main 发生在人工验收通过之后、打标签/发布/分发之前；如果 main 自动部署，合并本身即部署，见下条。
- main 只接受已验证提交，优先快进合并；这样 main 与验收对象是同一个提交。
- 如果 main push 会自动部署，合 main 就是部署动作：必须先取得部署授权，合并后立即核对运行版本和健康状态。
- 如果 main 不自动部署，合 main 只是晋级；部署另行执行。
- 由于 main 自动部署而需要验证时，应在 dev、候选分支或 staging 完成验收，不能先合 main 再验收。
- 验收未通过、授权未取得或远端存在未知分叉时，不合 main。

## 8. 发布、部署与分发

- 发布标签指向最终 main 提交；标签创建后不移动。
- 部署使用已验收的产物；不要在部署时重新构建一个不同版本。
- 分发前核对文件名、版本、校验值、可见性和访问权限；首次公开发布可能需要单独确认。
- 部署后核对运行版本/SHA 和健康状态；发布后核对实际可下载或可安装产物。
- 桌面应用如果打标签后 CI 重新构建，安装包必须能反查到同一提交；必要时直接发布已验收产物或核对校验值。
- 一个远端成功、另一个失败时，只补失败端，不重复已完成的外部动作。

## 9. 交付报告

       版本：
       范围：
       清理：文档 / 测试 / 文件 / 函数 / 孤儿代码 / 临时产物
       本地检查：
       CI：有 / 无 / 未运行原因
       构建：有产物 / 无构建产物
       性能或包体积：
       人工验收：环境、版本、结果
       合并 main：提交/SHA
       部署或分发：
       未验证或阻塞：
       回滚方式：

报告要区分“已通过”“未运行”“无法验证”。没有 build、没有 CI 不是错误，写成不存在的通过才是错误。

## 10. 停止条件

出现以下情况时停止交付并报告，不要继续推进：

- 没有备份就执行不可逆迁移。
- 清理范围不确定，可能删除动态加载或仍在使用的代码。
- 测试或验收使用真实用户数据，且没有授权和隔离。
- 工作区有未审阅的无关改动，无法保证提交范围。
- 远端存在未知分叉，准备强推或覆盖他人提交。
- 缺少交付所需的密钥、签名、权限或目标环境。
- 构建产物与验收产物不一致。
- 人工验收未通过，或 main 自动部署但未取得部署授权。
- 用户没有授权提交、推送、部署、发布或分发。
