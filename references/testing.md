# 测试策略与预算

测试是风险控制，不是工程成熟的装饰，也不是默认交付物。AI 辅助开发很容易生成大量测试、镜像实现细节、复制类型检查或锁死还会变化的行为；这些测试会消耗 token、拖慢收尾，并制造新的维护负担。

## 基本原则

- 日常开发不新增测试，不跑全量测试套件。
- 已有且直接相关的测试可以做定向运行；定向运行不等于新增测试。
- 只有用户明确要求当前版本进入版本收尾，才集中整理、补充和运行测试。
- 测试代码本身也要维护；不能只计算“有没有测试”，要计算它是否保护了真实、稳定、代价高的失败。
- 不设覆盖率目标。覆盖率高不等于关键风险被覆盖。
- 不为了每个改动写测试；一个行为只保留能防止真实回归的最低层测试。

## 开发阶段

### 默认动作

- 做与改动相关的类型检查、编译、格式检查和构建。
- 手动运行一次改动路径，确认正常路径和明显失败路径。
- 对已确认的 bug 记录最小复现：输入、预期、实际、环境和风险。
- 记录必要的截图、日志或命令输出；不要截图或粘贴整页无关日志。

### 允许的窄例外

以下三类风险可以在开发阶段做最小验证或定向测试，而不等到收尾：

1. **不可逆数据操作**：删除、批量迁移、覆盖用户文件、恢复流程。
2. **权限与安全边界**：认证、授权、CSRF、路径穿越、密钥泄露、越权访问。
3. **已确认的高危 bug**：不验证就可能再次造成数据损失或生产故障。

例外只允许最小复现或一个目标测试，不扩展成完整测试套件；全量执行仍留在版本收尾。即使不做，也要留下可复现步骤和风险评估，不能凭记忆拖到以后。

## 收尾阶段

1. 盘点现有测试，标记保留、删除、重写和缺失。
2. 删除已放弃功能、重复覆盖、只锁实现细节、只验证文案/CSS/组件结构的测试。
3. 只为本次改动、已确认缺陷和关键失败路径补最小测试。
4. 先跑目标测试，再跑项目约定的完整检查；中途改代码只重跑受影响项。
5. 记录新增、删除、保留、运行过、跳过和无法运行的测试及原因。
6. 清理测试产生的临时数据、截图、数据库和构建产物。

## 是否值得写测试

先问四个问题：

1. 它防止的真实失败是什么？
2. 这个行为是否稳定到值得锁定？
3. 是否有更便宜的层能覆盖，例如类型检查、构建或一次手动验证？
4. 如果删掉它，风险是否真的增加？

如果第 1 或第 4 个问题答不上来，默认不写。

| 场景 | 默认 | 建议层级 |
| --- | --- | --- |
| 稳定的 API/数据契约 | 写 | 契约或集成测试 |
| 已确认的回归 bug | 写一个 | 回归测试 |
| 数据迁移、删除、恢复 | 写 | 集成测试或隔离演练 |
| 权限、认证、安全边界 | 写 | 失败路径集成测试 |
| 并发、重试、幂等、超时 | 写关键场景 | 集成测试 |
| 复杂纯函数的边界条件 | 视情况 | 单元测试 |
| 普通 CRUD、类型已覆盖的字段 | 不写 | 类型检查/构建 |
| UI 文案、颜色、间距、组件结构 | 不写 | 人工检查 |
| 框架接线、生成代码 | 不写 | 构建/启动检查 |
| 一次性脚本、原型、脚手架 | 不写 | 运行一次 |
| 外部 API 正常路径 | 可写替身测试 | 契约测试；真实验收另记 |

## 测试预算

- 一个行为或一个已确认缺陷只保留一个主要测试；不要为每个代码路径复制多层测试。
- 能用集成测试覆盖的真实行为，不再补同义单元测试；反之亦然。
- 不写只验证 mock 调用次数、内部函数名、组件结构和源码字符串的测试。
- 不为覆盖率数字补充无关测试；测试停止条件是风险已覆盖，不是数字达标。
- 测试失败先核对需求、断言和夹具；不要为了让旧测试通过而削弱权限、文件保护或当前行为。
- 测试数据必须可丢弃；真实用户数据、生产数据库和真实群消息不能作为自动测试夹具。
- 全量套件在收尾运行一次；编辑过程中只做定向检查，避免反复消耗。
- 对文档、注释和纯文案改动，默认不跑测试；使用对应构建或链接检查。

## 反模式

- 测试实现细节，而不是用户可观察行为。
- 用快照锁死容易变化的 UI，而不是验证稳定的业务结果。
- 为简单 getter、常量或框架代码写测试。
- 同一个行为同时保留单元、集成和端到端三层重复覆盖。
- 用绿测替代真实环境验收。
- 测试需要生产密钥、真实用户数据或不可重复的外部状态。
- 为了让测试通过而修改产品行为，却不先确认需求。
- 只汇报“测试通过”，不说明运行了哪些、跳过了哪些、为什么。

## 报告模板

       测试变更：新增 / 删除 / 保留
       运行命令：
       通过：
       跳过或无法运行：
       未覆盖风险：
       临时数据清理：

报告要区分“通过”“未运行”“不适用”。没有运行测试时直接说明，不要用“应该没问题”代替证据。
