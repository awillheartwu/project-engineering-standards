# 文档规范与预算

文档是接口，不是任务副产品。每份文档都要有读者、职责和更新责任；没有消费者的文档会变成错误信息的来源。

## 文档预算

| 文档 | 唯一职责 | 适用项目 |
| --- | --- | --- |
| README | 这是什么、怎么运行、下一步看哪里 | 所有项目 |
| AGENTS / CONTRIBUTING | 怎么开发、提交、验证和遵守边界 | 有 agent 或多人协作 |
| 运维 / runbook | 部署、备份、恢复、回滚和排障；执行细节见 references/operations.md | 常驻服务、NAS 项目 |
| 架构 / 领域说明 | 稳定边界、数据模型和关键流程 | 多模块或复杂数据项目 |
| ADR | 难以逆转、未来会追问原因的决策 | 只在真正重要时 |
| CHANGELOG / release notes | 用户可感知的变化 | 有版本和交付 |
| ROADMAP | 只放未完成事项 | 有明确后续计划 |
| 用户指南 / 数据维护 | 安装、配置、使用、清理 | 插件、桌面应用、对外工具 |
| 临时分析 / handoff | 本次任务的过程记录 | 仓库外或忽略目录 |

小项目一份 README 就够；本地工具最多加 AGENTS；常驻服务再加运维和 CHANGELOG；桌面、插件再加安装和用户指南。ADR 不是每个决定都写。

## README 的最低结构

README 是门面，不是完整手册。默认回答六件事：

1. 这是什么、给谁用；
2. 为什么存在，解决什么问题；
3. 最小可用的开始方式；
4. 接下来该读哪里；
5. 运行要求、边界和已知限制；
6. 当前状态和维护方式。

README 的风格由**项目类型和主要读者的第一动作**决定，不按“技术版/用户版”二分平均铺开。首屏只放主要读者马上要做的事，其他内容通过链接进入专题文档。

| 项目类型 | 主要读者 | README 风格 | 首屏重点 | 放 docs 的内容 |
| --- | --- | --- | --- | --- |
| 对外桌面/插件/Web 工具 | 普通用户 | 使用优先 | 下载/安装、最短上手、常见流程、数据位置、支持 | 架构、开发、API、部署、内部实现 |
| 专业工具/API/SDK | 集成方、专业用户 | 集成优先 | 安装、最小示例、配置、兼容范围、限制 | 完整 API、内部模块、架构细节 |
| 常驻服务/后台系统 | 运维、部署者 | 运维优先 | 启动、环境、健康检查、备份恢复、回滚 | 架构、SLO、事故记录、内部设计 |
| 自用工具/内部系统 | 维护者 | 技术/运维混合 | 运行命令、配置、数据路径、部署/备份、开发入口 | 详细设计、ADR、CI、工作流 |
| Skill/文档仓库 | 维护者、agent | 维护者优先 | 技能名、调用方式、入口地图、状态、维护规则 | 各 reference、设计理由、案例 |
| 一次性脚本/原型 | 作者 | 最简 | 运行入口、输入输出、限制 | 不建 docs；必要时代码注释 |

专业用户和维护者要分开：专业用户需要配置、API、兼容性和升级方式；维护者才需要模块划分、状态机、测试和发布细节。README 不写完整功能清单、架构细节、完整 changelog 或重复 AGENTS 内容；命令必须可执行，链接必须指向当前入口。

优先保留一个 README。只有市场页面或发行包确实要求两种入口时，才增加第二个入口文件；它应只做导航，不复制事实。所谓“技术版本”更适合放在 DEVELOPMENT、ARCHITECTURE 或 AGENTS，而不是再维护一份 README.dev 与 README 同步。

## 创建门槛

新建文档前先回答：

1. 谁会读它？
2. 它帮助读者做什么决定或操作？
3. 能不能更新现有文档，而不是新建一份？
4. 谁负责在代码变化后更新它？

答不上来就不建。任务总结、审计报告和实现计划留在对话、issue、PR 或仓库外的 work 目录；不要自动变成永久文档。

## 文档生命周期

- 创建：先搜索现有文档；确定读者和唯一职责；从 README 或 AGENTS 链接过去。
- 更新：行为、配置、接口或运维方式变化时更新；没有变化不重写。
- 审查：版本收尾时列出新增、修改、删除的文档，检查命令和链接。
- 删除：过期、重复、没有读者的文档直接删除或合并；历史交给 Git。
- 索引：文档超过五六份时维护一个 docs/README 索引；少量文档不需要索引。
- 生成：OpenAPI、typedoc 等生成物明确标记，不手工编辑。

## Sprawl 信号

出现以下情况时，先审计而不是继续写：

- 多份文档回答同一个问题。
- REQUIREMENTS、DESIGN、IMPLEMENTATION_STATUS、ROADMAP 互相重复。
- 文档写着“当前”，代码已经变化。
- 完成事项仍留在 ROADMAP。
- 每次任务都新增一份总结或计划。
- 小工具也有十几份 docs。
- 文档没有入口，只能靠文件名猜。
- 命令、路径和截图已经失效。

## 清理流程

1. 列出已跟踪文档，按类型、读者、最后更新时间和引用关系分类。
2. 标记保留、合并、删除、归档；不要按文件名猜。
3. 检查 README、AGENTS、代码注释、CI 和脚本中的引用。
4. 合并重复内容，删除过期内容，把一次性分析移出仓库。
5. 检查命令、链接、路径和截图。
6. 文档清理单独提交，不混在功能改动里。
7. 保留 CHANGELOG、release notes、仍有效的 ADR 和运维说明；不要重写历史。

## ADR 规则

- 只记录难以逆转、跨模块、会让人未来追问“为什么”的决策。
- 一页以内：背景、决定、后果、放弃的替代方案。
- ADR 创建后不修改历史结论；需要改变时新增 ADR 并标记取代关系。
- 普通实现选择、命名和一次性的 bug 修复不写 ADR。

## AI 协作规则

- 先搜索现有文档；能更新就不新建。
- 不按每次任务生成总结、审计、handoff 或“完整指南”。
- 不复制 README、AGENTS、CHANGELOG 的内容。
- 临时分析放在仓库外或忽略目录；需要长期保留时再提炼进现有文档。
- 文档不是工作量的证明；没有读者就不写。
- 版本收尾时报告文档增删改，未更新就明确说明。

## 当前校准

- reYunPlex：README、AGENTS、docs 索引、架构、运维和流程说明职责较清楚，保持精简。
- DiscordManager：README + ROADMAP，属于克制的小项目文档形态。
- SceneVault：文档较多但主题不同；79 个 work 文件未入库，临时分析边界正确。优先检查 PROJECT_CONTEXT、ARCHITECTURE、DATA_MODEL、CAPTURE_WORKFLOW 是否重叠。
- lirating：优先检查 REQUIREMENTS、DESIGN_PROPOSAL、IMPLEMENTATION_STATUS、ROADMAP 是否在回答同一个问题；用户指南、数据维护、CI、发布说明可以保留。
- AVNDB：多份 account roadmap、execution plan 和一次性验收记录容易变成历史堆积；当前计划与历史验收分开，完成项移出 ROADMAP。
- gsg：文档较少，不需要为了统一规范扩充。

这些判断会随项目变化；清理前重新检查引用和当前状态，不照抄旧结论。
