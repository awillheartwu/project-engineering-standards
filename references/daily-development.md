# 日常开发规范

日常开发的目标是让改动可理解、可检查、可回退，不是把每个改动都做成完整交付流程。项目状态、交付类型和规模轴决定使用哪些规则；测试按 references/testing.md 执行。

## 每次改动

| 阶段 | 必做 | 按需 |
| --- | --- | --- |
| 开始前 | 查看工作区状态、分支、相关文件、数据边界和已有约定；搜索相关文档 | 读取接口、迁移、部署或验收说明 |
| 修改中 | 只改任务范围；保留无关修改；把新代码放进正确模块 | 文件接近规模阈值时先抽职责，不继续堆 |
| 修改后 | format 改动文件；对相关包做 lint/typecheck/build；手动走一次改动路径 | 数据、安全或高风险 bug 的定向验证 |
| 提交前 | 审阅暂存差异；对实际暂存内容执行[隐私检查](operations.md#提交与推送前的隐私检查)；排除调试代码、生成物和无关格式变化 | 需要时拆分提交或补文档 |
| 提交 | 一个提交一个目的；说明为什么改，不只写改了什么 | 提交、推送分别按授权执行 |
| 推送前 | 按[隐私检查](operations.md#提交与推送前的隐私检查)核对候选文件树、全部待推送提交/标签及实际分发产物；历史含敏感信息时必须先清除并复查 | 首次推送或基线不明时覆盖拟推送引用的完整可达历史 |

## 格式化与检查

- 每个栈只保留一个 formatter，例如 TS/Vue 的 Prettier、Rust 的 rustfmt、Python 已选定的 Ruff 或 Black；不要两套互相覆盖。
- formatter 只处理改动文件；不要在一次功能改动中重排整个仓库。
- lint 管正确性、未使用变量、Promise 错误、空 catch、导入错误和框架陷阱；缩进、引号、换行交给 formatter。
- 关闭 formatter 与 lint 的冲突规则；不要维护两套审美。
- typecheck/build 与 lint 分开；日常只检查相关包，全仓检查放在收尾或 CI。
- 警告不能无限期堆积；要么修复，要么写明禁用原因。
- 文档、注释和纯文案改动不需要默认跑测试，使用对应的构建或链接检查。

## 重构

- 重构和功能改动分开提交；先保持行为不变，再改行为。
- 一次只拆一个边界清楚的职责；不要为了行数把文件平均切开。
- 保持公开接口稳定；必须改接口时，先确认调用方和数据影响。
- 大文件拆分优先处理高变更频率、混合状态、混合 I/O 和混合业务规则的区域。
- 拆分后检查依赖方向、导入路径、类型和构建；测试按风险在收尾或定向验证。
- 不在功能提交中顺手大规模重命名、移动目录或格式化无关文件。

## 错误、日志与数据

- 不写空 catch；错误至少保留上下文，并让调用方知道失败。
- 日志不输出密钥、Cookie、Token、真实用户隐私或不必要的完整路径。
- 涉及真实数据的删除、迁移、覆盖和恢复，先说明影响并备份；日常操作使用临时或样本数据。
- 配置放在仓库外；仓库保留可复制的示例，启动时校验关键配置。
- 外部依赖失败时应明确失败，不要静默返回空结果。
- 生产运行的安全、备份、事故和监控见 references/operations.md。

## AI 协作

- 用最小相关上下文工作，优先搜索和定点阅读，不默认扫描整个仓库。
- 不重写与任务无关的代码；不把“能生成”当成“应该改”。
- 不默认新增测试；测试是风险控制，不是完成任务的装饰。
- 修改后检查实际 diff，确认没有调试输出、无关格式变化和意外文件。
- 报告改动、验证范围和未验证项；没有运行的内容不要写成通过。
- 命令输出保持有界；失败时先定位原因，不重复无效重试。

## 文档

- 新增文档前先搜索现有文档；优先更新、合并或链接，不按任务额外新建总结。
- 每份文档要有明确读者和职责；临时分析、handoff 和一次性报告放在仓库外或忽略目录。
- 行为、配置、接口或运维方式变化时同步更新对应文档；没有变化不为了“完整”重写。
- 文档清理单独提交；不与功能改动混在一起。详细规则见 references/documentation.md。

## 性能与 CI

- 性能敏感改动先测基线再优化；首版可以不做完整压测，但长线运营前要定义性能预算。
- CI 保持一条主流水线；构建一次并复用产物，不在部署阶段重新构建。
- 镜像、安装包和 CI artifact 有保留上限；不制造重复大包。详细规则见 references/performance-and-ci.md。

## 日常完成标准

一个日常改动可以结束，至少满足：

1. 目标行为在预期路径上可用，明显失败路径有合理处理。
2. 相关 format/lint/typecheck/build 已执行，或明确说明未执行原因。
3. 没有混入无关修改、密钥、生产数据或构建产物。
4. 接口、配置或用户行为变化有对应文档更新，且没有新增重复文档。
5. 需要的数据备份、回滚或授权边界没有被忽略。
