# 性能与 CI/打包

性能不是所有项目的默认门槛，但长时间运行的服务和应用进入长线运营后，必须有可测的性能边界。CI 也不是越完整越好；它的职责是用最低成本提供可重复的检查、构建和交付。

## 性能的进入时机

| 阶段 | 做什么 | 不做什么 |
| --- | --- | --- |
| scaffold / prototype | 只保证功能可运行；必要时记录启动和内存的粗略基线 | 不建压测平台，不为假想流量优化 |
| 首版 | 先完成正确性和关键路径；记录启动时间、内存、镜像/安装包大小的基线 | 不因没有性能数字阻塞首版 |
| 长线运营 | 为 3–5 个关键路径定义延迟、吞吐、内存、CPU、包体积和 CI 预算 | 不对所有接口和每个页面建指标 |
| 性能敏感改动 | 先测基线，再改动，再对比 | 不凭感觉优化，不做无基线的重构 |
| 收尾 | 有预算才检查预算；没有预算就记录缺口 | 不在收尾临时造大规模压测 |

## 关键指标

| 类型 | 优先指标 |
| --- | --- |
| 常驻服务 | p50/p95/p99 延迟、吞吐、错误率、RSS/堆内存、CPU、启动时间、队列积压、数据库查询时间 |
| 桌面应用 | 启动时间、空闲/工作内存、安装包大小、大图库加载与搜索、后台 CPU、导入/导出时间 |
| 平台插件 | 宿主内存、包体积、重载时间、消息响应、报告生成时间 |
| 静态页面 | 构建体积、首屏加载、资源数量、缓存命中 |
| CI | 总时长、安装/构建耗时、缓存命中、镜像/产物大小、部署耗时 |

指标要绑定真实数据形状。测试数据可以使用脱敏样本或合成大数据，不能把生产数据库直接当夹具。没有基线的性能数字没有意义。

## 性能预算

- 只给关键路径设预算，例如登录、列表首屏、同步任务、归档、报告生成。
- 预算来自基线加合理余量，不照抄行业数字。
- 预算要写进项目文档，并说明数据规模、环境和测量方法。
- 回归超过阈值时先调查，不自动把整个发布判死；确认是真实退化再阻塞。
- 达到预算就停止优化；没有明确瓶颈不做微优化。

## CI 设计

- 一条主流水线足够；默认不做平台矩阵、重复构建和多套发布。
- 阶段分开：检查 → 构建/打包 → 人工验收 → 部署/发布。PR 只检查，不发布。
- 构建一次，按提交 SHA 打标签，后续部署和分发复用同一产物；不要在部署步骤重新构建。
- 使用 lockfile、固定工具版本和缓存；缓存包管理器与 Docker 层，不缓存密钥。
- 使用路径过滤和依赖图只构建受影响包；过滤规则要覆盖共享包变更，避免漏构建。
- 复杂部署逻辑放在脚本里，workflow 保持薄；脚本可本地运行、可审查。
- 性能基准不放在每次 push 的阻塞路径；按计划或手动运行，结果单独保存。
- 日志和产物有保留上限；不把 node_modules、完整缓存、测试截图和整页日志当 artifact。

## CI 审计清单

| 检查项 | 通过标准 | 常见问题 |
| --- | --- | --- |
| 工作流数量 | 一条主流水线；确需拆分时职责清楚 | 双仓库各一套；同一套安装/部署脚本复制多份 |
| 触发范围 | PR 检查；main 部署；路径过滤覆盖共享包 | 文档改动触发全量集成/E2E |
| Secrets 作用域 | 只进入需要的步骤和环境 | 测试、构建 job 持有生产数据库/Token |
| Runner 信任 | 自托管 runner 不执行不可信 fork 代码 | Docker socket runner 默认跑公开 PR |
| 构建次数 | 构建一次，按 SHA 标记，部署复用 | 测完重建，部署产物与验收产物不同 |
| 迁移与部署 | 迁移有备份和回退；部署独立可观察 | 迁移成功后应用部署失败，数据库领先 |
| 发布边界 | PR 不发布；标签/手动发布另授权 | main push 同时构建、迁移、部署、发布 |
| 并发 | 部署串行；取消不会留下半完成状态 | cancel-in-progress 在停止/启动之间取消 |
| 工具与缓存 | lockfile、固定版本、缓存包和镜像层 | 每个 job apt 安装同一套工具 |
| 包体积 | 运行镜像/安装包只含生产资源 | 开发依赖、测试、缓存、密钥进镜像 |
| 产物保留 | 只保留必要镜像/包，有清理策略 | 每次构建永久保留，artifact 博物馆 |
| 性能基准 | 计划或手动执行，不阻塞每次 push | 每个 commit 跑完整压测 |

审计时先看工作流和脚本，不先看行数；行数只用于发现重复。当前案例：gsg 的双仓库、生产迁移和部署耦合最需要收敛；lirating 的 release check 更适合 main/tag；AVNDB 需要 paths 过滤和 Playwright 缓存；DiscordManager 需要部署串行；reYunPlex 和 SceneVault 的结构可保留。

## 镜像与包体积

- 多阶段构建；运行阶段只装生产依赖，不包含源码、测试、文档、缓存和开发工具。
- 使用 .dockerignore；锁定基础镜像版本；非 root、只读文件系统、no-new-privileges 按项目需要启用。
- 合并只对运行时有意义的层；清理包管理器缓存；不要把密钥写进层。
- 选择 slim/distroless 等基础镜像时先验证原生依赖和调试能力；不为了最小体积牺牲兼容性或可排障性。
- 每个可部署服务保留一个镜像；用 SHA 和语义版本标签，保留最近 N 个，定期清理旧产物。
- 桌面/插件包排除测试、原型、设计稿、源码映射和开发文档；发布前检查干净安装体积。
- 不同时保留大量重复镜像、压缩包和 CI artifact；产物保留策略要写清。

## 反模式

- 没有基线就做性能优化。
- 每个 push 跑完整压测、全平台矩阵或重复构建。
- 测试通过的镜像和部署的镜像不是同一个产物。
- CI 里重复安装同一套工具、重复构建前端和后端。
- 运行镜像包含开发依赖、测试、缓存、密钥或完整源码。
- 为了追求最小镜像删掉调试工具、CA 证书或原生库，导致线上无法排障。
- 把生产数据、真实用户数据或不可重复外部状态当性能测试夹具。
- 保留每一次构建的镜像和 artifact，却不清理。

## 当前校准

- gsg：主要成本来自双仓库、双份 Compose/部署逻辑和 CI 承担过多编排；在自然重构点收敛为一条构建与部署链。
- reYunPlex：CI 保持薄，构建一次并部署已验收镜像；长线运行时关注启动、内存和镜像体积。
- SceneVault：重点看 Windows 启动、内存、安装包体积和大型截图库操作；CI 只构建一次安装包，实机验收另记。
- AVNDB：长线运行关注 p95 延迟、队列积压、worker 内存、数据库查询和镜像体积；首版不因没有压测阻塞。
- lirating：关注插件包体积、宿主内存、报告生成和重载时间；不需要服务器镜像指标。
- DiscordManager：关注容器启动、内存、镜像体积和 Discord 事件延迟；单容器足够。

这些是优先级，不是一次性全做。项目进入长线运营或交付成本明显上升时，再补对应预算。
