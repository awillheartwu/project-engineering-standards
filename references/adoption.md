# 项目落地与存量审计

规范只有落到项目定位卡和例外记录上才算生效。新项目从定位卡开始，存量项目先审计再收敛，不做一次性大重写。

## 定位卡放在哪里

- active 项目在仓库根放 PROJECT_PROFILE.md；已有 docs/ 的项目可以放 docs/project-profile.md，并在 README 或 AGENTS 链接。
- 很小的一次性工具可以把定位卡压缩成 README 中的几行，不强制单独文件。
- 规范仓库或 NAS 上的项目索引维护一行摘要：项目、状态、定位卡链接、交付形态、例外、下一次复核触发。
- 索引只做导航，不复制完整定位卡；完整内容留在项目仓库。
- 定位卡是决策记录，不是日记；项目状态、用户、数据、部署或交付变化时更新。

## 新项目入场

1. 写一句话目标和边界，确认它现在是 scaffold、prototype 还是 active。
2. 填责任面、运行面、数据面、协作面；不先选数据库、框架或 CI。
3. 选最低基线：一个仓库、一个可运行入口、SQLite/本地文件、按需的文档和验证。
4. 确定交付形态和分支模型；没有交付就不建发布流程。
5. 给每个高成本组件写消费者、触发和退出条件；没有消费者不引入。
6. 记录下一次验证：什么时候算 prototype 完成，什么时候进入 active。

## 存量项目审计

审计阶段默认只读，不改代码、不删文档、不动部署。

1. 收集事实：工作区状态、分支、用户/数据、运行方式、交付方式、CI、文档、测试、备份。
2. 填定位卡；先确认项目状态，再判断责任和基础设施是否匹配。
3. 找错配：低实际使用 + 高基础设施；高责任 + 无备份/无恢复；有交付 + 无版本来源；大文件高 churn；文档/测试重复。
4. 标记动作：保留、在自然重构点收敛、补安全/备份、冷冻、记录例外。
5. 一次只选一个自然重构点；不在功能改动中顺带大迁移。
6. 把结论写进项目索引和定位卡，明确下一次复核触发。

## 例外记录

规范允许时间受限的例外，不允许静默违反。例外至少包含：

       项目：
       规则：
       原因：
       当前范围：
       风险：
       负责人：
       复核/到期条件：
       收敛计划：

例如 gsg 在决定产品定位前，可以记录“双仓库/双 CI 例外”，明确它不适用于新项目，并在下一次架构收敛时复核。例外没有到期条件就会变成事实标准。

## 复核触发

不按日历自动重写；出现以下事件时复核：

- 新增真实用户、外部访问或不可重建数据；
- 开始常驻部署、外部分发或商业分发；
- 发生数据丢失、密钥泄露、长时间故障或迁移失败；
- 版本收尾发现新组件、文档或测试明显膨胀；
- 维护者变化、项目冷冻或准备退役。

## 存量项目顺序

1. 先补安全和数据恢复：备份、密钥、入口、回滚。
2. 再停止继续加码：冻结无消费者的组件和文档。
3. 然后在自然重构点收敛架构：合并重复仓库、拆大文件、减少 CI 重复。
4. 最后处理版本、兼容和分发细节。

已有项目不需要为了“整齐”立刻重写；先让边界、证据和恢复路径成立。

## 完成标准

一个 active 项目算完成落地，至少满足：

- 有定位卡和当前状态；
- 有交付形态、分支模型和验证方式；
- D1/D2 有备份与恢复说明；
- 有定位卡索引入口；
- 例外有范围、风险和复核条件；
- 下一个收敛动作明确，不靠记忆。
