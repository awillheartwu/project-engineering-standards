# 项目状态与默认基线

状态不是荣誉等级，而是决定最低交付要求。状态只影响“必须做什么”，不直接决定数据库、队列、框架或部署方式。

## 状态迁移

| 状态 | 进入条件 | 离开条件 |
| --- | --- | --- |
| scaffold | 只有想法、模板、空仓库或不可运行的代码 | 出现一条可运行的端到端路径，且用样本数据验证过，才进入 prototype |
| prototype | 核心行为可运行，但数据可丢弃，没有真实依赖者 | 出现真实使用、需要保留的数据或持续交付责任，才进入 active；放弃则进入 frozen 或删除 |
| active | 有真实使用、需要保留的数据，或明确的持续交付责任 | 暂停演进但仍需运行时进入 frozen；只有新需求和维护承诺同时出现才恢复 |
| frozen | 暂停演进，但仍需可运行、可恢复 | 有真实需求和维护承诺，并完成依赖与数据评估后，才恢复 active |

状态不按代码量判断。一个几十行的个人脚本可以处于 active；一个很大的模板仓库仍可能是 scaffold。

## 默认基线

| 要求 | scaffold | prototype | active | frozen |
| --- | --- | --- | --- | --- |
| Git | 预计保留超过一周时初始化 | 必须 | 必须 | 保留原历史 |
| 一条命令启动 | 有入口即可 | 必须 | 必须 | 必须写在运行说明中 |
| README / 使用说明 | 目标与边界 | 运行方式和样本数据 | README + AGENTS 或等价规则 | 运行、备份、恢复和限制 |
| 配置与密钥 | 不入库 | 不入库；提供示例 | .env.example；真实配置在仓库外 | 保留配置说明，不轮换无关密钥 |
| 数据备份 | 不需要 | 样本数据可丢弃 | 数据面 D1/D2 必须有备份和恢复路径 | 必须有可执行的备份与恢复说明 |
| CI | 不需要 | 不需要 | 共享或部署的代码至少一条 CI | 不新增 CI；保留已有检查能力 |
| 版本与发布 | 不需要 | 不需要 | 有交付就维护单一版本源；发布另按授权 | 保留最后可用版本 |
| 部署与回滚 | 不需要 | 不需要 | 常驻服务需要；桌面应用需要安装/升级边界 | 保留可运行产物和回退路径 |
| 测试 | 不需要 | 只验证原型行为 | 版本收尾按风险整理和运行；不要求每次改动都测试 | 不新增测试；保留关键恢复验证 |
| 观测与诊断 | 错误输出 | 足够定位原型失败 | 常驻服务有健康检查/日志；桌面应用有本地诊断 | 保留日志与恢复入口 |
| 兼容层 | 不写 | 不写 | 只兼容真实存在的旧客户端、旧数据或旧安装 | 只保留仍需要的兼容路径 |

## active 的最低承诺

一个 active 项目至少要做到：

1. 有唯一的代码来源和可复现的启动方式。
2. 真实配置与密钥不进入仓库；提供可复制的示例配置。
3. 需要保留的数据有备份和恢复说明；迁移前先验证备份。
4. 共享或部署的代码有一条可重复的 CI；本地检查、CI、部署和真实环境验收分别记录。
5. 有明确的版本来源；需要分发或部署时，标签、镜像或安装包能反查到提交。
6. 有交付就有回滚路径；常驻服务至少能判断是否存活，桌面应用至少能安装、升级和恢复数据。
7. 修改、提交、推送、部署、发布分别按授权执行；讨论和检查不构成发布授权。
8. 不保留没有消费者的高成本组件；组件清单在版本收尾时复核。

这些是“最低承诺”，不是技术选型。active 仍然可以是一个仓库、一个进程、SQLite 或本地文件。

## 何时升级为更复杂的工程

状态本身不触发升级。只有组件触发器触发时才升级：

- 数据出现多写者或跨服务事务，才考虑 Postgres。
- 任务需要跨重启恢复、多 worker、优先级或长时重试，才考虑持久队列。
- 出现独立扩容、故障隔离或独立 worker，才考虑服务拆分。
- 出现真实旧客户端或旧数据，才写兼容层。
- 出现外部分发，才需要安装包、正式发布和实机验收。

升级后要重新填写定位卡，并在组件清单中记录消费者和退出条件。

## 何时降级或冷冻

- 真实用户消失、数据可重建、交付责任结束时，可以回到更轻的基线。
- 暂停开发但仍有数据或运行依赖时，标记 frozen，保留运行、备份和恢复，不继续加功能。
- 降级不是删除历史；已有迁移和兼容路径只有在确认没有消费者后才能移除。
